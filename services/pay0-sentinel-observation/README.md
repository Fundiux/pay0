# Servicio aislado Sentinel

Node22, HTTP nativo, OBSERVE_ONLY, sin exports de Functions financieras. No se desplegó. Docker se construye desde raíz del repositorio: `docker build -f services/pay0-sentinel-observation/Dockerfile .`. Imagen final solo contiene dependencias Firestore/OIDC, core compilado y servicio; no Firebase Admin ni módulos financieros.

`npm ci --ignore-scripts` y `npm run build` dentro de este directorio. Build compara SHA256 normalizado LF de seis archivos TS contra `core-manifest.json`, valida imports y transpila copia a `.build/core`. Cambios del core requieren revisión y actualización explícita del manifest, jamás sincronización silenciosa. `.build` no se comitea. Build contenedor no necesita dependencias del monorepo.

Configuración obligatoria: OBSERVATION_PROJECT_ID distinto de pay-0-system, OBSERVATION_DATABASE_ID=sentinel-observation, PUSH_SERVICE_ACCOUNT=pay0-sentinel-push@PROYECTO.iam.gserviceaccount.com, PUSH_AUDIENCE URL HTTPS Cloud Run y ALLOWED_ORIGINS_JSON. Este último es una lista cerrada de objetos `{projectId,publisherId,logName,serviceName,revisions,roots,actors}`. Todos los arrays deben ser explícitos/no vacíos, sin wildcard. `PORT` default8080. Config inválida falla startup con código fijo.

Cada fila contiene exactamente un root y sus actores permitidos: no se acepta un producto cartesiano de roots y actores. Varios roots requieren filas separadas; el máximo del canario es8 filas. El contexto del evento debe coincidir con la fila autorizada y con el evento.

Solo `GET /healthz` y `POST /pubsub`; servicio Cloud Run privado mediante IAM. El push debe usar envelope Pub/Sub envuelto cuyo data base64 sea LogEntry JSON de cloud_run_revision. jsonPayload contiene exclusivamente `{schemaVersion:"PAY0-SECURITY-ENVELOPE@1",context:{rootId,actorUid},event:{...PAY0-SECURITY-EVENT@1}}`. Proyecto/logName/servicio/revisión/localidad y roots/actors se comparan con allowlist; publisherId viene del mapping, nunca del evento. OIDC se valida antes de leer body. JWT acredita push SA, no al productor: el sink/topic cerrado y backend sanitizado siguen siendo la frontera de confianza. No conectar reportes browser a este transporte.

Adapter staging de escrituras permite lecturas completas antes de commit. Una transacción agrega el contador global con límite60/minuto UTC y10000/día UTC a los límites core de root/actor; duplicados y rechazos no gastan contador. Si supera cuota, ninguna escritura del evento persiste. TTL Timestamp48h para quotas/admission/receipts y7d incidentes, limpieza eventual gestionada por plataforma. Retención no equivale a cero datos expirados en disco. Tres intentos SDK máximo; IAM custom get/create/update + begin/rollback, condicionado a DB exacta. Rol no se amplía automáticamente si falta algún permiso.

Los cuatro permisos IAM son `datastore.databases.get` (BeginTransaction/RollbackTransaction), `datastore.entities.get`, `datastore.entities.create` y `datastore.entities.update`. Begin/rollback son operaciones cubiertas por databases.get, no dos permisos adicionales inventados. [Tabla oficial Firestore IAM](https://firebase.google.com/docs/firestore/security/iam).

Startup comprueba email real de SA en metadata Cloud Run y rechaza ADC/emulator overrides; `npm start` fuera de ese runtime falla cerrado. Tests locales instancian factory HTTP y adapter fake, sin simular credenciales productivas. `/healthz` es liveness del proceso, no prueba de acceso IAM a Firestore.

Resultados permanentes inválidos/quota reciben ACK2xx y métrica agregada; store caído/circuito/timeouts reciben503. Timeout HTTP no cancela mágicamente una transacción ya iniciada: puede completar después del503; receipt hace segura la reentrega. Límite local4 requests simultáneos y120 intentos/minuto protege recursos, no es cuota global. Métricas salen una vez/minuto con enum, sin payload/token/IDs/stack. Publicar una observación nunca autoriza reintentar un efecto financiero.

Infra `infra/main.tf` propone proyecto nuevo con billing variable sensible, DB dedicada, SA observer/push, IAM limitado, Run privado min0/max1, topic+DLQ, subscription autenticada y sink origen deshabilitado por defecto. Debe usarse un digest de imagen revisado y publicado por el responsable; el módulo no construye ni concede credenciales de build al runtime. No hay rol detector en proyecto financiero. El provisionador necesita permisos de crear/vincular proyecto y desplegar, separados del runtime; revisar grants heredados. Importar proyecto si ya fue creado, no recrearlo. Estado Terraform y tfvars son locales sensibles, no Git. No ejecutar apply sin revisión central. Los recursos de presupuesto/alertas deben configurarse según responsable/canal aprobado antes de activar sink; no se inventa destinatario de notificación.

Bootstrap explícito: primer plan limitado al proyecto, APIs y `google_artifact_registry_repository.images`; revisión/aplicación central. Después un builder autorizado separado produce/publica imagen en `us-central1-docker.pkg.dev/PROYECTO/sentinel-images/observer`, se captura digest y se prepara segundo plan completo con sink apagado. No usar digest ficticio ni desplegar imagen placeholder con autoridad. Build credentials nunca pertenecen al observer. Si se usa registro externo, el revisor debe dar Reader al agente Cloud Run sobre ese repositorio exclusivamente; este módulo no lo hace. Dockerfile.dockerignore excluye secretos, históricos y demás monorepo del contexto enviado al builder.

Para Cloud Build, ejecutar `node scripts/stage-build.mjs`: crea un directorio nuevo `.build/context-*` con whitelist18 archivos y core verificado. Subir SOLO ese directorio, con `cloudbuild.yaml` incluido y sustitución `_IMAGE` del registro aislado. Nunca subir raíz del repo. El responsable debe aportar builder SA separado, permisos mínimos en repo/staging bucket y Logging, sin compartir runtime ni credenciales financieras. El script únicamente copia archivos locales: no crea builds ni sube código.
