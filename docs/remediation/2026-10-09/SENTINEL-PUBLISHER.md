# Publisher servidor: canario sintético y puerto futuro

Fuente implementada 2026-10-09, sin despliegue ni activación de sink por este agente. No es evidencia de productor remoto existente. La imagen/base de datos/IAM del detector se gestionan centralmente y no se modificaron aquí. Nuevo servicio separado `services/pay0-security-observation-publisher`; helper puro `functions/src/modules/securityObservation/publisher.ts`, sin import del index financiero, authGuard, Firebase Admin o núcleo Sentinel.

## Opción mínima implementada

Cloud Run privado en proyecto origen contractual **pay-0-system**, servicio propuesto `pay0-security-canary`, región us-central1, identidad propuesta `pay0-observation-canary@pay-0-system.iam.gserviceaccount.com`. Runtime Node22 HTTP nativo sin dependencias npm. Builder transpila una sola fuente TypeScript con SHA256 fijado en publisher-manifest.json; Docker final copia únicamente helper compilado y cuatro módulos runtime. Sin keys, secretos nuevos, .env ni acceso financiero.

POST `/canary` solo acepta petición vacía, sin query/Origin. El servidor fija root `canary-observation-root`, actor `canary-observation-actor`, origin SERVER_AUTH_DECISION y eventType AUTHORIZATION_DENIED. Es un **evento sintético de prueba**, no una denegación real a una persona. EventId SHA256 depende de revisión para probar deduplicación ante repetición; el timestamp refleja cada envío. No se promete deduplicación de costes de Logging. El receptor asigna publisherId `pay0-observation-canary-v1` desde allowlist, nunca desde cuerpo cliente. Solo enumera IDs sintéticos y tipos; sin texto libre, paths, cabeceras, IP, tokens o payload de proveedor.

Emite una LogEntry a `projects/pay-0-system/logs/pay0_security_observation`, recurso cloud_run_revision con project/service/configuration/revision del runtime y ubicación fija. Requiere K_SERVICE/K_CONFIGURATION exactos y K_REVISION válida; un plan CLI no acredita la revisión desplegada. Logging se escribe por endpoint REST fijo, `partialSuccess:false`; metadata primero verifica proyecto/email exactos, después obtiene token efímero con Metadata-Flavor. Redirecciones deshabilitadas, respuestas metadata acotadas y ningún error/token registrado.

Un AbortController de **3s compartidos** cubre metadata+token+Logging y aborta pendientes al terminar. No retries automáticos: timeout puede significar aceptación remota desconocida; cada intento fallido consume cuota. Límite local6/minuto,20 por vida del proceso y un inflight. Es un freno de canario, no cuota global persistente; instancias/revisiones/restarts pueden reiniciarlo. Se propone min0/max1/concurrency1,256MiB,timeout Cloud Run5s. Cuerpo vacío comprobado en250ms; headers máximo8KiB/32, timeout HTTP4s. Health solo comprueba proceso. Cuotas persistentes del detector siguen siendo independientes.

Default `OBSERVATION_PUBLISHER_MODE=DISABLED`; `CANARY_DRY_RUN` llama API real con dryRun y no genera evento persistido/exportado; `CANARY` escribe solo tras revisión central. Respuesta LOGGING_ACCEPTED significa aceptación API, no recepción/persistencia Sentinel. [Contrato entries.write](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/entries/write).

## IAM y origen: límites explícitos

Propuesta runtime: rol custom con **logging.logEntries.create** en pay-0-system, sin Editor/Owner, Firestore, Auth, Storage, secretos, Pub/Sub publish ni impersonación. La autorización documentada de writes se evalúa en el recurso proyecto que recibe entradas; no se afirma aislamiento por logName vía condición IAM no probada. Builder/deployer son identidades separadas; si Artifact Registry queda en proyecto aislado, permiso pull debe resolverse para el service agent de Cloud Run sobre repositorio exacto, sin dar autoridad financiera al runtime. [API permissions](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/entries/write), [IAM Logging](https://docs.cloud.google.com/logging/docs/access-control).

Cloud Run debe mantener invoker IAM y un binding exclusivo a operador/identidad revisada, nunca allUsers/allAuthenticatedUsers. El servidor confía en esa frontera de plataforma; el test loopback no la certifica. Metadata endpoint devuelve credenciales de la identidad de servicio asignada; no se usa keyfile. [Contrato runtime/metadata](https://docs.cloud.google.com/run/docs/container-contract#metadata-server).

`resource.labels` y context son afirmaciones del backend, no prueba criptográfica independiente de actor. Otra identidad con permiso de crear logs en proyecto origen podría fabricar labels/payload. El aislamiento de detector no elimina ese riesgo heredado del proyecto financiero. Por eso este lote usa solo root/actor sintéticos, allowlist exacta de servicio/revisión y OBSERVE_ONLY, sin restricciones/decisiones financieras. No conectar reportes del navegador a este transporte. Activación de observación real requiere revisar autoridades de logging origen y aceptar/documentar esa frontera.

## Integración y verificación central pendiente

1. Revisar digest de imagen y crear SA/rol mínimos fuera del agente. El script `scripts/render-plan.mjs IMAGE_DIGEST REVISION` produce únicamente JSON de propuesta, sin APIs ni apply. El servicio arranca DISABLED.
2. Desplegar privadamente tras revisión y leer metadatos remotos reales (servicio, revisión, cuenta e IAM efectivo). Registrar esa revisión en allowed_origins; no inventar productor para satisfacer configuración del detector.
3. CANARY_DRY_RUN: un operador revisado verifica identidad/API/permiso sin routing. No considerar esto prueba de sink/PubSub/Firestore.
4. Revisar coste/budget y contrato del detector; activar CANARY y sink únicamente por coordinación central. Emitir una observación sintética, comprobar receipt/incident/OBSERVE_ONLY y repetir mismo eventId para deduplicación. Verificar rechazos de otra revisión/root/actor y permisos negativos mediante pruebas autorizadas sin datos financieros. Desactivar canario después.
5. authGuard queda sin modificar. Lote posterior implementará adapter por puerto, posterior a una denegación ya decidida; uid de auth verificada, root del perfil releído, nunca request.data. No alterar throw/código/recovery ni esperar un proveedor sin presupuesto. No crear ciclos/import del núcleo detector. Para observación real, sustituir cuotas de canario por política explícita; los límites actuales no se presentan como cobertura productiva de authGuard.
